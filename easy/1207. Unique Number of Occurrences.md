# [1207. Unique Number of Occurrences](https://leetcode.com/problems/unique-number-of-occurrences/description/?envType=study-plan-v2&envId=leetcode-75)

## Intuition

Use a `HashMap` to store occurrence counts.<br>
The `key` is the array element, and the `value` is the number of times it appears.

After traversing the array, check whether the occurrence counts are unique.<br>
At first, a `List` was used for duplicate checking, but since `contains()` performs a linear search, it may become inefficient.

---

## Approach

1. Create a `HashMap` to store elements and their occurrence counts.
2. Traverse the array and update the count for each element.
3. Iterate through `map.values()` and check whether the count already exists.
4. If a duplicate count is found, return `false`.
5. If no duplicates exist, return `true`.

---

## Complexity
### Time Complexity
O(n²) — Since `List.contains()` runs in O(n), the overall complexity can grow to O(n²) in the worst case.

### Space Complexity
O(n) — A `HashMap` and a `List` are used to store occurrence counts and check duplicates.

---

## My Solution
```
class Solution {
    public boolean uniqueOccurrences(int[] arr) {
        HashMap<Integer, Integer> map = new HashMap<>();

        for (int n : arr) {
            map.put(n, map.getOrDefault(n, 0) + 1);
        }

        List<Integer> list = new ArrayList<>();

        for (Integer value : map.values()) {
            if (list.contains(value)) return false;

            list.add(value);
        }

        return true;
    }
}
```

---

## Review

`List.contains()` performs a linear search internally, which takes O(n) time.<br>
As the number of unique occurrence counts increases, the total time complexity can grow to O(n²) in the worst case.

To improve this, a `HashSet` can be used since it is designed for efficient duplicate checking.

---

## Revised Solution
```
class Solution {
    public boolean uniqueOccurrences(int[] arr) {
        HashMap<Integer, Integer> map = new HashMap<>();

        for (int n : arr) {
            map.put(n, map.getOrDefault(n, 0) + 1);
        }

        HashSet<Integer> set = new HashSet<>(map.values());

        return map.size() == set.size();
    }
}
```

### Comparison Summary

| | Before | After |
|---|---|---|
| **Time Complexity** | O(n²) | O(n) |
| **Space Complexity** | O(n) | O(n) |

---

## Performance Comparison

However, in actual runtime measurements, the original `List` solution may sometimes perform faster.

Looking at the constraints:

- `arr.length ≤ 1000`
- Value range: `-1000 ~ 1000`

This means the number of distinct values is capped at 2001.  
Since the input size is relatively small, the theoretical complexity difference may not significantly affect real-world performance.

On the other hand, `HashSet` internally uses a `HashMap`, which introduces overhead such as:

- Hash calculations
- Bucket management
- Additional memory allocation

Because of this overhead, an O(n) solution can still be slower for small inputs.

| Category | Original (`List`) | Optimized (`HashSet`) |
|---|---|---|
| Duplicate Check | O(n), but n is very small | Average O(1), but includes hashing overhead |
| Internal Structure | `ArrayList` | `HashSet` + internal `HashMap` |
| Practical Performance | Can be faster for small inputs | More beneficial for large inputs |

Actual performance is not determined solely by asymptotic complexity (Big-O).  
Considering input size and constant overhead is also an important part of real optimization.
