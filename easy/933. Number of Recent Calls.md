# [933. Number of Recent Calls](https://leetcode.com/problems/number-of-recent-calls/description/?envType=study-plan-v2&envId=leetcode-75)

## Intuition

Each call to `ping(t)` should return the number of requests within the recent 3000ms range `[t - 3000, t]`.

Since timestamps are guaranteed to arrive in increasing order, we only need to remove outdated requests from the front.

Therefore, a FIFO Queue is an efficient choice for this problem.

---

## Approach

1. Add the new timestamp `t` to the Queue.
2. If the front value of the Queue is smaller than `t - 3000`, it is outside the valid range, so remove it.
3. The remaining elements represent all valid recent requests, so return the Queue size.

````
        START: ping(t) called
                |
                v
    ┌─────────────────────────┐
    │ Add timestamp t to      │
    │ the back of queue       │
    │ queue.offer(t)          │
    └─────────────────────────┘
                |
                v
        ┌─────────────────┐
        │ queue.peek()    │
        │ < t - 3000 ?    │
        └─────────────────┘
             /      \
          YES        NO
           /          \
          v            v
┌─────────────────┐   ┌─────────────────────────┐
│ Remove oldest   │   │ Return queue size       │
│ timestamp       │   │ return queue.size()     │
│ queue.poll()    │   └─────────────────────────┘
└─────────────────┘             |
          |                     v
          └────────────────>   END
               repeat
````

---

## Complexity
### Time Complexity
O(1) — each timestamp is inserted into the Queue once and removed once.

### Space Complexity
O(n) — stores requests within the recent 3,000ms window.

---

## My Solution
```
class RecentCounter {
    Queue<Integer> queue;

    public RecentCounter() {
        queue = new LinkedList<>();
    }

    public int ping(int t) {
        queue.offer(t);
        while (queue.peek() < t - 3000) {
            queue.poll();
        }
        return queue.size();
    }
}
```

---

## Review

The core logic is already close to optimal.

However, using a data structure better suited for Queue operations can further improve memory efficiency and runtime performance.

### Improvement Points
- Replaced `LinkedList` with `ArrayDeque`
  - Avoids unnecessary node object allocation.
  - Uses less memory.
  - More cache-friendly and generally faster in practice.

---

## Revised Solution
```
class Solution {
    public boolean uniqueOccurrences(int[] arr) {
        HashMap<Integer, Integer> map = new HashMap<>();

        for (int n : arr) {
            map.put(n, map.getOrDefault(n, 0) + 1);
        }

        HashSet<Integer> set = new HashSet<>(map.values());

        return map.size() == set.size();
    }
}
```

### Comparison Summary

|                      | Before (`LinkedList`)                | After (`ArrayDeque`)                 |
| -------------------- | ------------------------------------ | ------------------------------------ |
| Internal Structure   | Node-based linked list               | Array-based circular queue           |
| Memory Usage         | Requires prev/next pointers per node | Uses contiguous array storage        |
| CPU Cache Efficiency | Lower                                | Higher                               |
| `offer()` / `poll()` | O(1)                                 | O(1) (faster in practice)            |
| Actual Runtime       | Relatively slower                    | Faster                               |
| Queue Suitability    | General-purpose list                 | Optimized for Queue/Deque operations |


---

## Performance Comparison



The improvement is not about changing the algorithm itself, but about refining the implementation:
Choosing a better-suited data structure leads to cleaner code and naturally better performance.

Even with the same time complexity,
implementation details can influence actual runtime behavior and memory efficiency.

### Key Improvements
- **Improved Memory Efficiency**
    - Switched from `LinkedList` to `ArrayDeque` as the underlying data structure.
    - `LinkedList` allocates a separate node object (with two pointers) per element,
      whereas `ArrayDeque` stores elements in a contiguous array — reducing per-element overhead.
    - → Lower memory footprint and better cache locality.

- **Stronger Encapsulation**
    - Added `private` modifier to the `queue` field.
    - → Prevents unintended external access and follows standard OOP practices.

- **Same Algorithm, Better Runtime Behavior**
    - The logic of `offer → while(peek < t-3000) poll → size` remains identical.
    - However, `ArrayDeque`'s array-based layout improves CPU cache efficiency
      compared to `LinkedList`'s pointer-chasing traversal.
    - → Same time complexity O(1) amortized, but faster in practice.
